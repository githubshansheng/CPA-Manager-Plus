# Онлайн-миграция SQLite в MySQL

[简体中文](../../operations/mysql-migration) | [English](../../en/operations/mysql-migration) | [繁體中文](../../zh-TW/operations/mysql-migration) | [Русский](./mysql-migration)

Manager Server может сохранять стандартное поведение SQLite, перенося всю историю во внешнюю базу MySQL. После переключения SQLite остаётся хранилищем конфигурации и кэшем недавних данных. Эта возможность рассчитана на один процесс Manager Server; она не развёртывает встроенный контейнер MySQL и не выполняет автоматическое переключение при сбое.

## Поддерживаемая целевая система

- Поддерживается официальная MySQL 8.x, начиная с 8.0.12; MariaDB и MySQL 9.x не поддерживаются.
- Схемы MySQL 8.0.17+ используют `utf8mb4_0900_bin`. Версии 8.0.12–8.0.16 автоматически используют доступную для них NO PAD, чувствительную к регистру и диакритике `utf8mb4_0900_as_cs`. Сеансы используют UTC, строгий режим SQL и `innodb_strict_mode=ON`.
- Учётной записи необходимы права `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `ALTER`, `DROP`, `INDEX`, `REFERENCES` и `TRIGGER` на выбранную схему. CPAMP проверяет их случайной пробной таблицей, а не полагается только на разбор `SHOW GRANTS`.
- Если включено binary logging и обычная учётная запись схемы получает Error 1419 при создании trigger, потребуйте от DBA установить и сохранить `log_bin_trust_function_creators=ON` либо поручите установку trigger DBA с необходимыми административными правами; не предоставляйте `SUPER` учётной записи приложения.
- Для внешней MySQL по умолчанию используется проверка идентичности сертификата. Отключение TLS отображает предупреждение безопасности и требует повторного подтверждения.
- Значение `max_allowed_packet` должно быть не менее 4 MiB. Предварительная проверка останавливается, если какая-либо авторитетная строка SQLite не помещается в один пакет протокола MySQL.

## Маршрутизация данных

В обычном режиме каждая авторитетная запись фиксируется в SQLite и добавляет полную группу Outbox в той же транзакции. Рабочий процесс затем применяет её к MySQL. После переключения чтения бизнес-запросы предпочитают MySQL и возвращаются к SQLite только при классифицированных ошибках подключения или доступности. Ошибки SQL, схемы, прав, сканирования и данных никогда не скрываются резервным возвратом.

SQLite постоянно хранит настройки, учётные данные администратора, параметры подключения к базе данных, цены моделей и их context/service tiers, а также псевдонимы API Key. После переключения и защищённой очистки прочие бизнес-данные по умолчанию остаются в кэше 15 дней, тогда как MySQL хранит всю историю. Активные, ожидающие или незавершённые действия, периоды охлаждения, проверки и записи жизненного цикла квот не удаляются по давности.

## Перед началом

1. Создайте резервную копию всего каталога данных CPAMP, включая SQLite/WAL/SHM, `database-control.json.enc`, его `.bak` и `data.key`.
2. Настройте независимое резервное копирование MySQL и выполните тренировочное восстановление.
3. Убедитесь, что целевая база данных пуста или полностью совместима с manifest схемы, показанным CPAMP.
4. Подтвердите достаточность ёмкости, `max_allowed_packet`, лимитов подключений и срока хранения резервных копий для всей истории.
5. Выполняйте работу в период низкой нагрузки. Окончательная проверка ненадолго приостанавливает Collector и фоновые рабочие процессы записи.

## Три этапа миграции

### 1. Проверить MySQL и включить двойную запись

Откройте **Система → Топология базы данных**, укажите адрес, базу данных, учётную запись, пароль, режим TLS и сертификат CA, затем выберите **Проверить MySQL**. Сохраните подключение и выберите **Включить двойную запись**.

Серверная часть проверяет версию, набор символов/collation, UTC, строгие режимы, размер пакета и фактический доступ DDL/DML. Она создаёт полную схему, копирует каждое поле конфигурации, включает SQLite Outbox и запускает синхронизацию в реальном времени. На этом этапе бизнес-чтения всё ещё используют SQLite.

Пароль никогда не возвращается в браузер и не записывается в журналы. Если при следующем сохранении оставить его пустым, текущий пароль сохранится.

Если после обновления схема MySQL устарела, остановите репликацию и миграцию, убедитесь, что MySQL не обслуживает чтение или запись, затем выберите **Пересоздать схему MySQL**. Интерфейс последовательно покажет два опасных подтверждения с именем текущей базы; серверная часть дополнительно проверит цель, имя базы, routing generation и ключ идемпотентности. После подтверждения CPAMP удалит все таблицы, представления, триггеры и данные в настроенной базе и создаст актуальный schema manifest. Сама база не удаляется; SQLite не изменяется; данные не копируются, репликация не включается и маршрутизация не переключается. Перед операцией обязательно создайте резервную копию MySQL.

### 2. Перенести историю

Выберите **Перенести исторические данные**. CPAMP копирует каждую авторитетную таблицу в порядке внешних ключей при стабильном watermark первичного ключа/rowid, сохраняя явные ID, NULL, исходный JSON, тела неудачных ответов, данные клиента/IP, token, service tiers, цены, проверки, действия, периоды охлаждения и поля жизненного цикла квот.

Размер пакета по умолчанию — 1 000 строк, он ограничен бюджетом чтения 4 MiB; слишком большая строка получает отдельный пакет. Устойчивые checkpoint поддерживают паузу, возобновление, повтор и перезапуск процесса. Исторические пакеты не могут перезаписать более новые строки, уже доставленные Outbox. Затем MySQL перестраивает агрегаты, projection, индексы и поисковые данные из авторитетных строк.

Раздел **Журнал задач миграции** в системной информации показывает сохранённые задачи, текущий этап и статус, строки/байты/запросы по каждой таблице и полную хронологию выполнения. Ошибки фонового процесса дословно добавляются в неизменяемый журнал аудита; возобновление очищает только текущее предупреждение и не удаляет предыдущую причину сбоя. Те же записи доступны администратору через `GET /v0/management/databases/migrations?limit=20`.

### 3. Проверить и переключить бизнес-чтения

Дождитесь backlog `0`, затем выберите **Проверить**. CPAMP ненадолго устанавливает глобальный барьер записи, доводит MySQL до итогового watermark Outbox и сравнивает схему, число строк, диапазоны первичных ключей, внешние ключи, нормализованный по полям SHA-256, token, число успешных/неуспешных операций и стоимость, рассчитанную по зафиксированному снимку прайс-листа.

Validation token и **Переключить бизнес-чтения** становятся доступны, только когда пройдены все проверки и контракт соответствия производных данных/поиска. Для переключения нужны текущие migration ID, token, цель и routing generation; устаревшие значения возвращают `409`. После переключения SQLite остаётся фронтовым уровнем записи по умолчанию и кэшем недавних данных.

## Очистка кэша

Плановая очистка по умолчанию отключена (флажок изначально снят), поэтому запуск и обновление не удаляют данные SQLite неявно. После явного включения администратором историю SQLite всё равно нельзя очищать до переключения чтения на MySQL. Когда переключение, проверка и watermarks синхронизации безопасны, предварительно просмотрите очистку, затем запустите ограниченную задачу очистки. Она автоматически приостанавливается, если MySQL недоступна, Outbox ожидает обработки, миграция не завершена или проверка устарела. На существующих установках сохраняется ранее сохранённое состояние переключателя.

Ручное переключение основной базы записи, очистка SQLite и перестроение кэша SQLite — опасные операции. Помимо текущих routing generation и ключа идемпотентности, каждый запрос должен возвращать целевой backend, migration ID и validation token, показанные в UI. Серверная часть повторно сверяет их с зашифрованным контрольным файлом и устойчивым состоянием миграции; отсутствующее или устаревшее подтверждение никогда не выполняется.

Онлайн-удаление делает страницы SQLite пригодными для повторного использования; оно не уменьшает сразу физический файл `usage.sqlite`. System Info отдельно показывает физический размер, используемые страницы и повторно используемое пространство. Не запускайте внешний `VACUUM` и не заменяйте файл базы данных, пока активен Manager Server.

## Сбои и восстановление

- **Прерывание MySQL:** SQLite продолжает принимать записи, а Outbox накапливается. Резервные ответы содержат заголовки `X-CPAMP-Data-Source`, полноты и покрытия кэша, а UI продолжает показывать заметное предупреждение о частичных данных.
- **SQLite не может записывать:** CPAMP переходит в состояние только для чтения/ожидающего переключения и отправляет предупреждение. Он никогда не повышает MySQL автоматически; администратор должен проверить цель, epoch и watermarks перед подтверждением переключения при сбое.
- **Перестроить SQLite из MySQL:** это восстанавливает всю конфигурацию и только бизнес-кэш за последние N дней. Перед атомарной заменой под коротким барьером записи создаётся и проверяется временная база SQLite. Это не перенос всей истории обратно в SQLite.
- **Восстановление SQLite после записей MySQL:** перед обратным переключением дождитесь обратного выравнивания Outbox и проверки. Записи из старого fencing epoch отклоняются.

Если backlog существует и 60 секунд нет прогресса, проверьте подключение, диск, блокировки и права. Через 120 секунд CPAMP помечает рабочий процесс как `stalled`. Никогда не запускайте второй процесс Manager Server, чтобы «ускорить» миграцию.
